# `templates/` — Governance Document Templates

Templates for point-in-time security documents that require human review and
cannot be fully generated by a script. Copy the one you need into your
project's `security/` folder and fill in the placeholders.

## Files

| File | Purpose | Can it be auto-generated? |
|---|---|---|
| `CYB_REPORT_TEMPLATE.md` | Point-in-time security audit report, standards-mapped (OWASP/ASVS/CIS), with executive summary and per-finding remediation. | **Mostly yes** — `../audit/run-audit.ps1` / `.sh` auto-generates a populated version of this structure (`CYB_report_<timestamp>.md`) from the current scan results. Use this template directly only if you're writing a deeper manual review (pentest response, architecture-level findings) that goes beyond what the automated scanner checks. |
| `BIA_ACP_TEMPLATE.md` | Business Impact Analysis addendum — Confidentiality/Integrity/Availability (ACP) rating, impact analysis, sign-off. | **No** — the ratings require a human business judgment call. `../audit/scaffold-bia-acp.ps1` / `.sh` scaffolds the boilerplate and auto-fills the "known open items" table from the latest audit report, but the rating sections must be completed by a person and routed for Cyber Security validation. |

## Usage

```powershell
# CYB report — usually just run the audit instead (see ../audit/README.md);
# use the template directly only for a manual/deeper review:
Copy-Item CYB_REPORT_TEMPLATE.md C:\path\to\repo\security\CYB_report_2026-09-16.md

# BIA/ACP — always scaffold via the script so open findings get pulled in:
powershell -ExecutionPolicy Bypass -File ..\audit\scaffold-bia-acp.ps1 -RepoPath C:\path\to\repo -AppName "My App"
```

Both templates mirror the real structure used in the SE_DI_PIP project's
`security/` folder (`CYB_report_*.md`, `BIA_ACP_addendum_*.md`) — see those
files for a fully worked, filled-in example of each.

Both templates retain a tooling-attribution block for the
[AI & Developer Security + Deployment Playbook](https://github.com/alouatiq/ai-dev-security-playbook)
and [Dr. AL OUATIQ H.](https://www.alouatiq.com). Project teams should keep
their own names in the auditor, author, and sign-off fields; the attribution
does not identify the playbook maintainer as a developer of their project.
